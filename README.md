# TDLibKit 2

TDLibKit 2 is a Swift concurrency façade over the native C++ API of upstream
[TDLib](https://github.com/tdlib/td). It does not move the old JSON transport to
another boundary: requests and responses remain `td_api::object_ptr` values from
Swift through `td::ClientManager`.

The TDLib source is a Git submodule pinned to
`d1085f9cebc5a62379991ae1652673954f229c1f` (TDLib 1.8.67). The pinned
`td_api.tl` and the C++ generated by TDLib itself are the only schema sources.

## Package graph

```text
TDLibKit (Swift, static product, C++ interop enabled)
└── TDLibCxxBridge (C++ RAII façade)
    └── TdStatic.xcframework (static Td::TdStatic dependency closure)
```

`TDLibKit` is the canonical static product for one-executable apps and maximum
final-linker dead stripping. `TDLibKitShared` is an opt-in dynamic product over
the same `TDLibKit` module and targets. Use it when an application and its app
extensions must load one shared copy instead of statically linking TDLib into
every executable. Consumers still write `import TDLibKit`.

For an app plus extension, embed `TDLibKitShared.framework` only in the
containing app. Link the extension to the same product without embedding it and
include `@executable_path/../../Frameworks` in the extension runpaths.

There is no dependency on Swiftgram/TDLibFramework and the former
`TDLibKitDynamic` wrapper package remains removed. `TdJson`, `TdJsonStatic`,
`tdjson`, the `td_send/receive/execute` C API,
and Foundation JSON serialization are forbidden by `scripts/check-native.sh`.

The prebuilt `TdStatic.xcframework` is distributed as a GitHub Release asset.
`Package.swift` pins both its immutable release URL and SwiftPM checksum, so
package consumers do not need this repository's local build output.

## Swift usage

The manager is an actor. It owns one native `td::ClientManager`, uses globally
monotonic non-zero `UInt64` request IDs, routes updates only when
`request_id == 0`, and has one blocking receive pump. The pump waits in TDLib;
it does not busy-wait.

```swift
import TDLibKit

let manager = TDLibClientManager()
let client = try await manager.createClient()

let option = try await client.send(TDNativeRequests.getOption(name: "version"))
if case .optionValueString(let version) = option {
    print(version.value)
}

try await client.close()
await manager.shutdown()
```

Generated `TDNative…` models are thin owned views. A nested view shares the
native root lifetime and never exposes a borrowed TDLib pointer. Scalars and
strings/bytes are copied when read. Models share immutable native storage and
can be copied, retained, and reused across requests, including nested views
obtained from responses. Each parent or request receives an independent native
copy of its object inputs; constructing or sending it never invalidates the
original models. Only the `TDRequest` itself is single-use: create a new request
for each send, reusing the same model parameters as needed.

The deterministic generator covers 3,205 TL declarations (2,183 objects,
1,022 functions), 211 unions, 592 schema-documented optional object pointers,
primitive/object/nested vectors, bytes, int53, and Int64. TL `int32` is exposed
as Swift `Int` and checked exactly at the native `Int32` boundary:

```sh
./scripts/tdlib-native.sh generate
./scripts/generate_native_schema.py
./scripts/generate_native_schema.py --check
```

Generated files must not be edited by hand.

## Building TDLib

Initialize the pinned submodule, then build the pinned OpenSSL 3.1.5 matrix from
Python-Apple-support commit `6f43aba0ddd5a9f52f39775d0141bd4363614020`:

```sh
git submodule update --init Vendor/td

./scripts/tdlib-native.sh openssl \
  --platform all \
  --output-root .build/tdlib-native/openssl-pinned \
  --xcode /Applications/Xcode-26.6.0.app

./scripts/tdlib-native.sh build \
  --platform ios --configuration Release --optimization oz --lto off \
  --openssl .build/tdlib-native/openssl-pinned/ios --jobs 8 \
  --output .build/tdlib-native/products/ios/libTdStatic.a
```

The released iOS Simulator library is universal so Xcode can build the
dynamic `TDLibKitShared` product for both Apple Silicon and Intel simulator
destinations. Build the arm64 and x86_64 simulator archives separately, then
combine them with `./scripts/tdlib-native.sh universal` before creating the
XCFramework. Pass `--arch x86_64` to both the `openssl` and `build` commands for
the Intel archive; arm64 remains the default.

The build invokes only the `tdclient` target and its `Td::TdStatic` dependency
closure. Tests, JNI, .NET, shared libraries, and JSON targets are disabled or
not built. `./scripts/tdlib-native.sh verify` inspects every architecture in the
XCFramework for forbidden JSON objects and symbols. Upstream license texts are
retained as `Documentation/TDLib-LICENSE.txt` and
`Documentation/OpenSSL-LICENSE.txt`.

Swift package consumers must enable C++ interoperability on targets importing
TDLibKit:

```swift
swiftSettings: [.interoperabilityMode(.Cxx)]
```

For an Xcode application target, set `SWIFT_OBJC_INTEROP_MODE = objcxx`.
Native C++ consumers may depend directly on the `TDLibCxxBridge` product; the
public header intentionally exposes RAII façade classes, not TDLib inheritance,
templates, or rvalue-reference APIs.

## Verification and size

```sh
./scripts/check-native.sh
swift test
./scripts/test.sh iOS-simulator 26.5 'iPhone 17 Pro' test
./scripts/test.sh watchOS-simulator '' '' build
./scripts/test.sh tvOS-simulator '' '' build
./scripts/test.sh visionOS-simulator '' '' build
./scripts/check-size.sh
```

The current same-host thinned arm64 Release result is 22,603,200 bytes versus
the measured 50,337,127-byte TDLibKit 1.5.2 baseline (-55.10%). See
[the size report](Benchmarks/SizeHost/RESULTS.md) and
[the architecture decision](Documentation/Architecture.md).

Migration from the 1.x Codable API is intentionally breaking; see
[Migration 2.0](Documentation/Migration-2.0.md).

## Current risks

- The released XCFramework contains arm64 device slices for macOS, iOS,
  watchOS, tvOS, and visionOS. The iOS Simulator slice is arm64+x86_64; the
  remaining simulator slices are arm64. On SDK-only machines without those
  simulator runtimes, `scripts/test.sh` uses SwiftPM cross-compilation. SwiftPM
  6.3 cannot currently plan the dynamic product for an `xros` triple, so the
  visionOS SDK-only gate requires an installed visionOS runtime or a newer
  SwiftPM implementation.
- ThinLTO produced a build candidate but raw bitcode archives cannot be passed
  to `xcodebuild -create-xcframework -library`; it remains unselected until a
  tested static-framework packaging path exists.

No commit, tag, release, or remote publication is performed by these scripts.
